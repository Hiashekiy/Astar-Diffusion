# 引导场构建加速：三种传播实现与基准

对应 `src/guidance_stage2/propagation.py`、`scripts/benchmark_propagation.py`

## 1. 结论先说

| 结论 | 数据 |
|---|---|
| **NumPy 同步传播与 heapq 逐位等价** | 20 张真实地图上 `max|ΔF| = 0.0e+00`；与 Stage 2A 存盘场差 1.1e-07（float32 存储误差） |
| **在真实 20 张地图上整体快 2.07×** | heap 86.5 ms → vectorized 41.8 ms（A 2.70×、B 2.64×、D 2.90×、**C 0.94×**） |
| **不是普适更快** | 合成 256×256 迷宫：vectorized **慢 15.9×**（0.03×）；低偏心率稀疏房间图也慢 2–3× |
| **桶式队列没有收益** | 0.90–1.10×，因为瓶颈是 Python 邻居循环而非堆操作 |
| **两项微优化就把 heap 提速 2.2×** | 去掉多余的连通域 BFS + 用预计算邻居表：heap 192.6→86.5 ms，vectorized 106→41.8 ms |
| **落到 Stage 3 端到端** | 场构建 **6.57 → 2.32 ms（2.8×）**，B3 总耗时 2.89 ms，**反超 A\* 的 4.01 ms** |

## 2. 三种实现

### 2.1 heap（基线，精确）

多源最大堆 Dijkstra。改动两点：
- 邻居遍历改用 `grid._nbr` 预计算表（原来每个节点调一次 `grid.neighbors()`，会构造 numpy 视图）；
- 删除多余的连通域 BFS：未到达的自由格本来就停留在 `-inf`，最后统一置 NaN 即可，等价且省一次全图 BFS。

### 2.2 vectorized（主推荐，精确）

```python
F_{t+1}(x) = max( F_t(x), max_{y in N4(x)} [F_t(y) - lam] )
```

- 四个方向**同步**更新（每个方向都读上一轮的场），与更新顺序无关；
- `steps_per_round=4`：每轮连做 4 次同步算子再判收敛。只改变检查频率，不改变不动点，省掉大部分 Python 往返；
- 障碍格每轮强制置 `-inf`，所以传播不穿墙；
- 收敛判据 `np.array_equal(work, field)`。

复杂度 `O(ecc × H × W)`，而 heap 是 `O(V log V)`。这就是"开阔图快、长廊图慢"的根因。

### 2.3 bucket（Dial，量化）

利用 `F = 1 − λ·C`、`C(x) = min_i[d + (1−w_i)/λ]` 把最大值扩散转成带偏移的多源最短路，键为
`scale·d + round(scale·(1−w)/λ)`，量化误差 `≤ λ/(2·scale)`（scale=16 → 6.25e-04，实测 6.2e-04，与理论一致）。

**实现细节（踩过的坑）**：不能直接用 `scale+1` 的环形桶。种子偏移是任意分布的整数（0–800），环形容器会在条目到期前复用到同一槽位而把它们当陈旧条目丢掉，导致大面积不可达。改用**层堆 + 层内列表**（`heapq` 只存"当前有节点的层号"），对稀疏键也正确，并且把每节点的堆操作降为每层一次。

## 3. 合成基准（64 / 128 / 256，64 源点，λ=0.02，最优值取 2 次重复）

| size | 地图 | heap ms | vectorized ms | 加速 | bucket ms | 加速 |
|---:|---|---:|---:|---:|---:|---:|
| 64 | clutter | 4.93 | **2.19** | 2.25× | 4.86 | 1.01× |
| 64 | maze | **2.87** | 4.59 | 0.62× | 2.98 | 0.96× |
| 64 | rooms | **0.30** | 0.61 | 0.49× | 0.27 | 1.10× |
| 128 | clutter | 20.25 | **8.20** | 2.47× | 19.40 | 1.04× |
| 128 | maze | **11.82** | 119.99 | 0.10× | 11.67 | 1.01× |
| 128 | rooms | **1.02** | 2.90 | 0.35× | 1.04 | 0.98× |
| 256 | clutter | 87.32 | **56.93** | 1.53× | 80.52 | 1.08× |
| 256 | maze | **49.32** | 1494.90 | 0.03× | 49.93 | 0.99× |
| 256 | rooms | **4.60** | 14.70 | 0.31× | 5.08 | 0.90× |

误差列（CSV 内）：vectorized 全部 `0.0e+00`；bucket 除整数对齐的 rooms 图（3.3e-16）外均为 `6.2e-04`。

**测量方法学的坑**：第一版基准把计时和 `tracemalloc` 放在同一个调用里，结果 64×64 的 heap 被测成 72 ms（真实 ~5 ms），而且不同实现的失真程度不同。现在计时与内存分开测，并且 `--repeats` 取最优值。

## 5. `auto` 选择与它的边界

`propagate_auto`：自由占比 ≥ 0.55 → vectorized，否则 heap（owner 需求时强制走 heap，因为 vectorized 无法廉价给出主导源）。

**这个规则是在真实 20 张图上标定的，不是通用规律。** 反例就在合成基准里：rooms 256（自由占比 0.92、偏心率仅 81）vectorized 慢 3.2×——因为这种图自由格多但堆的松弛次数极少，而同步传播每轮都要扫全图。

没有便宜的通用预测器：heap 的成本取决于"成功松弛次数"（clutter 2.7 µs/格，rooms 0.11 µs/格，差 25 倍），不是自由格数；vectorized 的成本取决于 `ecc × H × W`。要稳健，应在**每个地图指纹上各跑一次取更快者并缓存**，而不是用解析模型猜。

## 6. 三项微优化的实测

| 优化 | 效果 |
|---|---|
| 去掉多余连通域 BFS（未达格自然 `-inf`→NaN） | heap 192.6 → 86.5 ms（2.2×，20 图合计） |
| `grid._nbr` 预计算邻居表替代 `grid.neighbors()` | 同上（两者都在这一版里） |
| `return_owner=False`（搜索只需场） | owner 账本约占总时间 10–15%，基准里单独记录 |
